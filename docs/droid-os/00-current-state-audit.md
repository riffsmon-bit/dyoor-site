# Droid OS — current-state audit

Status: Phase 0 engineering assessment, 6 September 2026. Not an independent smart-contract security audit or permission to activate financial execution.

Follow-up evidence: [verified live Season 2 source and transfer-authority findings](10-transfer-authority-decision.md) now supplements this initial audit. The deployed runtime matches Sourcify's exact-match artifact; the worktree's same-named Season 2 source is a different revision. No collection upgrade or source replacement was performed.

## Executive decision

Preserve the existing Season 2 collection and deployed owner-controlled Droid Account V1. Build an additive, read-only Droid OS first. The project already has real NFT-bound wallets, but does **not** have a verified, deployed capability-based autonomous execution system. An off-chain `autonomous` flag cannot add that authority to the existing account.

The observed production site is `dyoor.fun`. The new specification names `dyoor.xyz`; that hostname could not be reached from this audit environment. This is not evidence about domain ownership. No domain, metadata URI, secret, role, contract, or production configuration was changed.

## 3. Exact existing Droid Wallet

Source: `contracts/hoodyoor/src/droid/DroidAccountV1.sol` and `DroidAccountRegistry.sol` in the broader local branch. Website adapters: `lib/droid-accounts/{config-runtime,server-runtime,client}.ts`.

The account is an ERC-6551-style 173-byte minimal proxy with immutable token-binding footer. The canonical registry derives its address from implementation, salt, chain, collection and token ID. The facade fixes implementation, zero salt, Monad 143 and Season 2. It allows the current NFT owner to create the account idempotently; the underlying canonical registry can also permissionlessly predeploy the same correctly bound address.

For Droid 11, facade and canonical registry both derived **`0x6B7E71B10EE63bbA4c460e80C7569EaF3Fb129Cd`**. Its deployed footer references the expected implementation and `(143, Season2, 11)`. Observed balance: **0.01 MON**; state counter: **4**; account owner equaled `ownerOf(11)`. ERC-165 and valid/invalid signer probes behaved as expected. The implementation and facade hashes match `deployments/monad/canary-11-20260814.json`; this is not a new reproducible source-to-bytecode attestation.

Account V1 supports owner-only `execute` and atomic bounded `executeBatch` (maximum 32 calls), ordinary CALL only, native/ERC20/ERC721/ERC1155 custody, current-owner ERC-1271 signatures, reentrancy protection and owner-cycle/burn failure handling. There is no AI signer, project withdrawal role, session-key executor or autonomous capability entrypoint. Owner-only arbitrary CALL is existing wallet functionality; it must not be exposed to AI or MCP.

The public production account configuration reported `activationEnabled=false`, mode `off`, and no activation token allowlist. Existing account 11 remains deployed. Site activation flags are not on-chain custody restrictions.

## 4. Exact ownership-authority path

`chain + collection + tokenId → configured canonical derivation → account.token() → collection.ownerOf(tokenId) → account.owner() → msg.sender == current owner`.

Account execution enforces current ownership on-chain, not cached indexer ownership. ERC-1271 verifies against the current owner. Direct implementation use, wrong-chain bindings, burned tokens, cycles or failed owner resolution fail closed. The canonical identity key already exists in Solidity and `lib/droid-economy/identity.ts`: `keccak256(abi.encode(chainId, collection, tokenId))`.

UI helpers recheck ownership before activation/withdrawal. However, funding helpers accept an account address without independently rederiving its full NFT binding; withdrawal helpers also need exact facade/account-token cross-checks, not only matching owner addresses. Harden these before presenting them as canonical Droid OS flows.

Critical limitation: transferring the controlling NFT revokes old-owner **account calls and signatures**, but does not erase ERC20 allowances or external NFT operator approvals previously granted by that account. Existing tests do not prove universal revocation of every external spender. Also, owner A → B → A cannot invalidate historical grants using owner address alone: the account state counter is not a controlling-NFT transfer nonce. These are explicit blockers for transferable autonomous authority.

## 5–6. Strategy and Achievement Registry compatibility

Local `HoodYoorStrategyRegistry` supports versioned strategy descriptions, risk/metadata URIs, adapter references, asset allocation weights and owner-controlled selection through the economic identity registry. It does not execute assets or enforce the proposed reserves, daily budgets or capability grants. Reuse as a descriptive catalog/selection reference, not as financial consent. A previous owner's strategy selection must not authorize spending by the next owner.

The local Achievement Registry supports versioned definitions, issuer/manager roles, evidence hashes and bounded reward modifiers tied to Droid identity. It can inform a read-only achievement adapter. It is not a wallet authorization system.

Live `/api/droid-economy?chainId=143&tokenId=11` returned all six economic addresses empty: Droid Registry, Asset Registry, Strategy Registry, Revenue Vault, Rewards Distributor and Achievement Registry. Strategies and achievements were empty; financial feature flags were disabled. This proves **unconfigured in the observed production integration**, not that no deployment exists anywhere. Do not fabricate live strategies or achievements.

## 7–8. Energy and Trait Lab safety

Energy Bank is a nontransferable, address-scoped points ledger with credits, spends and role-controlled/EIP-712 authorization. The application combines chain data with server-side debit/accounting records. Its display decimal scale does not make Energy money, gas, investment return or transferable Droid capital. In Droid OS, show it explicitly as the connected owner's Energy unless a separate allocation design is approved.

Trait Lab uses mutable trait records, versions, rendered images, canonical original metadata, wallet signatures, current ownership and Energy accounting. Background/base Droid restrictions and fail-closed protections must remain intact. The current client has a fresh account-state burn guard that blocks active/funded Droid wallets or unknown account state. This is a UI safeguard, not a collection-level prohibition against bypassing the UI and burning the parent NFT. A burned parent can strand wallet assets.

Preserve `lib/s2-trait-lab.ts`, Energy accounting, mutable metadata storage and existing acceptance/recycle signatures. Do not replace current rerolled metadata with original IPFS metadata. Visual traits may influence presentation but never grant a financial capability.

## 9. Existing swap/trading reuse

`lib/droid-trading/server.ts` is a tightly bounded **SIMULATION_ONLY** MON→USDC Kuru experiment for token 11, at most 0.001 MON, bounded slippage and short quote lifetime. It performs calls/estimates and computes projected balances; this is not a comprehensive account-context state-diff simulation. It does not establish sellability, reserve protection or a production risk assessment.

Local `DroidOwnerTradingV1.sol` is an owner-directed allowlisted guard candidate, not permissionless autonomous execution. Production owner-trading address is empty and trading/broadcast/autonomy flags are off.

Legacy quote code (`netlify/functions/quote.js`, `lib/swap.ts`, static swap code) includes Kuru Flow/Nad.fun routing and upstream transaction normalization. Its quoting knowledge may be reused after review; upstream arbitrary target/calldata must not become trusted AI execution authority. World escrow is peer NFT trading, not a marketplace sniping adapter.

Official [Kuru addresses](https://docs.kuru.io/contracts/Contract-addresses) agree with the observed router/market. [Kuru architecture](https://docs.kuru.io/contracts/Architecture-overview) includes upgrade/governance considerations: address matching is insufficient without implementation/configuration verification. No relevant Seaport/marketplace buy adapter was verified or enabled by this audit.

## 10–12. Backend, indexing and AI

Production uses Next/Netlify, Netlify Blobs and local-file fallbacks, public RPC providers, metadata/image gateways and optional Supabase quest storage. The broader branch includes SQLite-backed Discord services and a standalone game. Live database migration state, RLS, backup restoration, worker availability and all service quotas were not verified.

`src/lib/storage/fileStore.ts` provides both fallback reads and strict reads. Strong-consistency Blob reads do not provide a transaction spanning policy, budget reservation and execution records. Do not reuse read-modify-write Blob accounting as a financial daily-limit lock.

Account indexing uses bounded log scans, checkpoints, retries and partial-data status. Portfolio discovery covers configured assets, not all possible holdings or approvals. Existing checkpoint writes need leases/CAS and reorg/block-hash handling before financial reliance. Public `syncActivity=1` can request index work and needs cost/rate isolation. Indexing must remain non-authoritative.

Source schedules include Energy indexing/reconciliation, World sales/burn/push, OpenSea refresh, bounty settlement and Discord notifications. Broader-branch Monad activity dispatch/background workers are not present in current website main; live deployment of those workers remains unknown. Existing operator airdrop/deployment jobs were not run.

No first-party working OpenAI, Anthropic, xAI, Bankr, Gemini, DeepSeek or MCP integration was found. No shared opportunity engine, typed financial intent pipeline, provider orchestrator or capability execution system was found. A text match for `bankRaw` is not a Bankr integration.

Secret interfaces include wallet-session HMACs, Privy configuration, Energy signing/operator keys, Netlify storage credentials, Pinata/OpenSea API credentials, Discord credentials, Supabase service role and deployment/admin interfaces. Only names/interfaces were inspected; production secret values were not read or changed. AI workloads must not inherit this broad credential set.

## IPFS and World compatibility

The repository contains the self-hosted Kubo/IPFS gateway infrastructure and previous pin/backup records for `ipfs.dyoor.fun`. Immutable trait layers and original metadata are distinct from mutable live Trait Lab records in Netlify storage. This audit did not perform a new complete recursive pin/restore verification. It does not claim every mutable reroll is now an immutable IPFS object.

World's wallet session and fresh holder checks are appropriate social access primitives, not authorization over a particular Droid. A wallet can remain a valid World member after selling one Droid because it owns another. World names are wallet-bound, not the canonical NFT identity. Preserve compatibility through adapters rather than coupling chat/game services to wallet execution.

User-reported follow-up at 09:26 local: Trade desk stays on a loading skeleton. Investigate after this audit; do not infer the root cause from the screenshot. The push panel also truthfully reports missing VAPID server configuration; no secrets should be generated or changed under this audit.

World escrow takes custody of the offered Season 2 NFT while an offer is open. Under canonical `ownerOf`, the escrow contract therefore temporarily controls that NFT's Droid account; the maker must not retain synthetic off-chain authority over it. Successful trade transfers the Droid account's control/assets along with the parent NFT. Cancellation returns control. Droid OS needs explicit account-asset/approval disclosure before offering a funded Droid; this audit and the loading fix do not change escrow semantics.

Highest-priority findings are architectural blockers, not evidence that exploitation has occurred. An owner-only wallet deliberately permits its owner to transact broadly; that does not make it suitable for unrestricted AI tools.
